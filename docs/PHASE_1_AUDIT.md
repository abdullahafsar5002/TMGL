# TMGL Phase 1 Audit

**Date:** 2026-09-17
**Auditor:** AI Architect
**Scope:** Complete project audit — web, PWA, Android, database, auth, security

---

## 1. Project Overview

**TMGL — Toruk Maktu Golf League** is a golf league management platform with:
- React 18 + TypeScript web application (Vite)
- PWA with service worker (vite-plugin-pwa + Workbox)
- Native Kotlin/Jetpack Compose Android application
- Supabase backend (PostgreSQL + Auth + RLS)
- 4-role RBAC system (public, player, league_manager, super_admin)

---

## 2. Existing Architecture

### Web Application
- **Framework:** React 18 + TypeScript (strict mode)
- **Build:** Vite 5 with path aliases (`@/` → `src/`)
- **Styling:** Tailwind CSS 3.4 with custom TMGL color palette
- **Routing:** React Router DOM v6 with public/protected route separation
- **State:** React Context (AuthContext only) — no global store
- **Backend:** Supabase JavaScript client (`@supabase/supabase-js`)
- **Service Layer:** `lib/league.ts` (Phase 2 CRUD) and `lib/competition.ts` (Phase 3 CRUD)
- **Deployment:** Vercel (SPA rewrites configured)

### PWA
- **Manifest:** Generated by vite-plugin-pwa (`manifest.webmanifest`)
- **Service Worker:** Workbox-generated, autoUpdate mode
- **Icons:** SVG format at 192x192 and 512x512
- **Display:** standalone, portrait orientation
- **Theme:** #0B3D2E (golf green)

### Android Application
- **Framework:** Hybrid — Capacitor scaffold + Native Kotlin/Compose
- **Actual UI:** 100% Jetpack Compose (NOT WebView)
- **Language:** Kotlin 2.0.21
- **UI Toolkit:** Jetpack Compose + Material3
- **Backend:** Supabase Kotlin SDK (direct PostgREST, not via Capacitor)
- **Min SDK:** 24 (Android 7.0), Target SDK: 35 (Android 15)
- **Build:** Gradle 8.14.3 + AGP 8.13.0
- **Signing:** Release keystore configured via `key.properties`

### Database
- **Provider:** Supabase (PostgreSQL)
- **Tables:** 14 tables (profiles, seasons, divisions, players, teams, team_members, courses, course_holes, tournaments, rounds, matches, scorecards, scorecard_holes)
- **RLS:** Enabled on all tables with role-based policies
- **Auth Trigger:** `handle_new_user()` auto-creates profile row
- **Functions:** `get_user_role()` SECURITY DEFINER (avoids recursive RLS)

## 4. Architecture Findings

### Web/PWA Architecture
- **Clean separation:** Service layer isolates all Supabase queries
- **Consistent patterns:** ServiceResult<T> return type, error handling, loading states
- **Mobile-first:** 44px touch targets, safe area insets, bottom navigation
- **PWA valid:** manifest.webmanifest with correct icons, standalone display, service worker
- **Build output:** 640KB JS (gzip 156KB), 29KB CSS (gzip 6KB)

### Android Architecture
- **NOT a WebView wrapper:** Fully native Kotlin/Compose UI
- **Dual architecture:** Capacitor scaffolding exists but is vestigial (not used)
- **Native features:** Splash screen, edge-to-edge, Material3 theming
- **Data layer:** 3 repositories (Auth, Competition, League) calling Supabase directly
- **Screens:** 14 screens (Splash, Auth, Home, Tournaments, Matches, Scoring, Leaderboard, Players, Teams, Profile, Settings)
- **Known issue:** ScoringScreen score submission is not wired to Supabase (comment-only)

### Database/RLS
- **Comprehensive RLS:** All tables have policies for read (public/owner) and write (manager/admin)
- **Recursive RLS fix:** `get_user_role()` SECURITY DEFINER function prevents infinite recursion
- **Auth integration:** Auto profile creation via database trigger
- **No service-role exposure:** Only anon key used in client code
